# People: face records, corrections and scan queue

Adds the storage and security model for People (face recognition). Additive only:
no existing table, policy or row is altered or deleted, and no photo is scanned.
Recognition is opt-in per album owner (`face_settings.enabled`, default false), so
the new `photos` trigger queues nothing until an owner enables it.

## Objects

- Extensions `vector` (pgvector 0.8.6 available on the instance) and `pg_trgm` (1.6).
- Role `personal_photos_face_worker`: LOGIN, NOBYPASSRLS, no password set here, created
  `ADMIN snowflake_admin` (required by Snowflake Postgres to configure the role, as for
  `personal_photos_maintenance`). The credential is provisioned separately as a
  Snowflake secret for the face job. Database `CONNECT` and `public` schema `USAGE`
  come from the existing `PUBLIC` grants; the explicit grants emit a harmless "no
  privileges were granted" warning when run by `snowflake_admin`.
- Tables: `face_settings`, `face_people`, `faces`, `face_assignments`,
  `face_rejections`, `face_corrections`, `face_scan_runs`, `face_scan_queue`.
- Triggers: `enqueue_face_scan` and `retire_faces` on `photos`; `retire_faces` on
  `photo_trash`; `guard_face_assignment` and `guard_confirmed_face`.

## Security model

- Owner scope: an owner (or main admin) reads their own people data; writes also
  require `can_write`. Composite foreign keys make cross-owner assignment impossible.
- Shared viewers see a person name only when the owner enables `share_names`, the
  person is named and not hidden, the match is `auto` or `confirmed`, and the viewer
  can already read the photo (`read_photo`). Rejections, corrections, settings,
  suggested matches and the queue are never visible to them.
- Public links: no policy grants any people data to an identity-less session.
- `faces.embedding` is excluded from the application's column grants. Embeddings are
  only readable by the face worker and maintenance.
- Corrections win: the worker cannot update, delete or cascade-delete a confirmed
  assignment, and no role can assign a face to a person it was rejected for.
- Manual tags (`faces.source='manual'`) let an owner tag a person the scanner
  missed, with a drawn box or name-only. The app may insert only manual rows, only on
  photos it can edit, owned by that photo's album owner, attributed to the caller.
  Manual rows never hold an embedding, so they are never matching references, and
  the worker cannot delete them. Detected-face geometry cannot be edited by the app.
- The worker reads only catalog path/owner columns of `photos` and `events`.
- Scan runs are main-admin only; one active run at a time (partial unique index).

## Lifecycle

Faces are keyed by `photo_id` without a cascading foreign key because Trash deletes
and restore re-inserts the `photos` row under the same id. Face data is removed (and
crops queued in `stage_cleanup`) only when neither `photos` nor `photo_trash` holds
the id, mirroring `retire_video_playback`.

## Compatibility

Current and previous application versions do not reference these objects and are
unaffected. The `photos` trigger is a no-op until an owner opts in. Index builds run on
empty tables. Vector dimensions are not fixed in this migration; an ANN index is added
by a later migration once a model is selected. At current library size exact search is
sufficient.

## Verification

`npx vitest run tests/people-rls.test.ts` covers fail-closed, owner separation, the
embedding column grant, shared-name opt-in, public links, read-only identities,
main-admin scan control, correction guards, manual-tag permissions and integrity,
worker boundary, queueing and Trash
lifecycle. After apply, as `snowflake_admin`:

```sql
SELECT extname, extversion FROM pg_extension WHERE extname IN ('vector','pg_trgm');
SELECT relname, relrowsecurity FROM pg_class WHERE relname LIKE 'face%' ORDER BY 1;
SELECT count(*) FROM face_scan_queue; -- expected 0 until an owner opts in
```

## Recovery

Roll application code back freely; these objects are unused by older versions. If the
feature must be withdrawn, disable it by setting `face_settings.enabled=false`. Data
removal is a separately reviewed forward migration (drop triggers first, then tables,
then role); do not edit or delete this applied file.
