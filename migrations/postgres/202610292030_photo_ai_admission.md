# Short-transaction photo AI admission

Compatibility: additive maintenance-only tables and a SECURITY INVOKER claim function. Deploy receipt recovery first. The library retains legacy claims unless `PHOTO_AI_LEASED_ADMISSION=true`; the production manifest explicitly enables fair claims. Both modes now acquire the same `ai-categorization` advisory lock, preventing overlap with legacy workers during rolling upgrades or rollback. Keep that compatibility lock while legacy releases remain rollback candidates, and use identical admission limits across schedulers.

Configuration: library fallback limits are fleet 3, tenant 1, local workers min(3,fleet); production explicitly sets all three to 8. The per-owner ceiling of 8 preserves lone-owner throughput; the SQL claim sequence rotates owners when multiple owners have eligible work. Production uses explicit 100,000-claim fleet and per-owner hourly ceilings, counting cached reuse and retries as well as provider dispatch. These ceilings are operational guardrails, not a monetary budget or a throughput claim. Set explicit `PHOTO_AI_MAX_CLAIMS_PER_HOUR` and `PHOTO_AI_TENANT_MAX_CLAIMS_PER_HOUR`; the tenant value must not exceed the fleet value. These are conservative UTC-hour claim allowances, not dollar estimates: cache reuse, crashes and retries consume allowance too. Direct REST is required; there is no automatic warehouse fallback. Idle workers exit and rely on the existing wake loop for retries and the next quota window.

Verification: `tests/photo-ai-admission.test.ts` covers fleet/tenant limits, fair tenant rotation, hourly budgets, invalid limits, forbidden app access, lease recovery and stale publication. PGlite serializes its connections; this is SQL correctness evidence, not a multi-node concurrency or throughput test. The repeatable `npm run test:ai-admission-postgres` check uses a disposable loopback-only Docker Postgres 17 instance with synthetic data and eight real connections. Run `docker pull postgres:17` first. It verifies simultaneous limits, quota serialization, disconnect-before-commit rollback, persistence after a committed worker disconnect, lease reclaim, stale-token fencing and app-role denial, then removes the container. It accepts no remote database URL and calls no inference provider. This minimal-schema correctness check does not prove Snowflake multi-node throughput or full deployed-schema compatibility. The native check also verifies eight simultaneous lone-owner claims, a newly arriving owner receiving the next free slot, and old/new schedulers contending on the same lock. Before activation, verify the actual worker restart lifecycle and full-schema migrations in isolation. Individual claims commit before provider work; the existing scheduler holds one session connection for its compatibility advisory lock, as legacy mode already did. Existing model/prompt reuse and durable receipts remain authoritative for paid-inference recovery.

Rollback: switch the flag off through a normal release, retaining all leases, receipts and quota records. Do not expire leases or reset budgets to accelerate rollback. Leave the additive objects installed; app-role access remains denied. Apply through the normal reviewed migration and backup/restore checks.
