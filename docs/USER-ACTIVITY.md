# User activity and identity reports

The original schema came from setup/16-user-activity.sql; do not replay this frozen file. The Access Manager or read-only admin page is /admin/users-activity. Both the page and reporting API enforce the administrative read permission. Read-only administrators can view reports but gain no management permissions.

Authenticated app visits are sessions, not identity-provider logins. Activity arriving after 30 minutes of inactivity starts a new session. Active means reported within five minutes. HttpOnly, same-site cookies identify sessions; the server supplies usernames. Browser page reports are approximate, best-effort analytics, not a security audit. Browser input timestamps never enter the database. Only allowlisted paths (no query strings) are accepted. Views are queued on navigation and flushed shortly afterward or on the one-minute active/visible heartbeat; leaving the tab immediately can lose a view. Hidden/idle tabs send nothing.

Successful favorite, photo Trash, cover, labels, album edit/Trash, bulk, and upload-completion requests schedule server events after their response. Upload events now use stable deduplication keys as described below; request retries are not additional completed files. Existing access-management operations retain their separate durable audit journal. Caption contents, passwords, tokens, media URLs and user-agent/IP data are not recorded.

The dashboard shows 30 days of users, visits, photo/album views, UTC daily activity and the latest 200 events, filtered by exact username/type. Refresh is manual. Tracking and saved-report reads use Postgres. Administrative read/import permissions remain server-enforced under the configured permission authority. Cleanup is invoked by background maintenance, with a database guard limiting deletions to once per day. Detailed records and sessions older than 90 days are removed. No data is collected retroactively.

Analytics are best effort: loss during shutdown or database failure does not prevent the primary action. This is not a compliance audit log. The detailed usage and identity-import features below extend these base events.

## Detailed usage

Historical schema addition: `setup/17-detailed-usage.sql` (do not replay). This adds structured metadata and a timeline index in Postgres. Read-only admins retain report visibility only; administrative mutations still require their existing write guards.

- Video starts/errors and approximate foreground wall-clock watch seconds are recorded in the viewer and slideshow. Paused, hidden, stalled, seeking and suspended-device intervals are excluded. Browser events use retry IDs; queued batches flush during activity and best-effort on exit. Closing the browser or losing connectivity can lose the final interval. Client measurements are analytics, not trusted audit evidence.
- Searches store the validated query (up to 300 characters), scope, actual successful search source, result count, response duration and sanitized status on failure. Failed automatic searches retain mode `auto` because the completed source is unknown. Counts are API search requests; one UI action may search both albums and photos. No searches means no search collection work.
- Upload starts are counted when chunk zero is accepted. Completion reads the owned durable upload record, with actual bytes and success/duplicate result. A stable key per user, upload ID and event type deduplicates completion retries. Failure counts represent unique uploads with completion/processing failures; they may later succeed. Transient 429 processing contention is excluded. Preflight/browser-only failures and lost chunk requests are not counted as completed processing failures.
- Explicit original downloads and ZIP requests record requested file counts and original byte totals. Ordinary photo/video playback, thumbnail fetches and Range requests are excluded. These are accepted download requests, not proof of completion or bytes delivered; ZIP overhead is not included.
- Reports offer 1/7/30/90-day filters, aggregate cards, daily usage, user selection and paginated timelines with event details. Cursor ordering retains PostgreSQL microseconds so same-time events are not skipped. Search queries are visible only to report-authorized administrators. Detail starts at deployment; old events are not backfilled.

Raw detail has 90-day retention. Provider login imports are explicit actions described below; saved reports do not re-query providers.

## Identity logs and retained summaries

Identity imports are manual, separately controlled by Access Manager permission. Read-only admins can view reports and export CSV, but cannot import either provider (enforced on the server).

- **Auth0:** reads the Management API using `read:logs`. The upstream scope is tenant-wide; only exact `AUTH0_GALLERY_CLIENT_ID` login successes/failures are saved. Known Auth0 IDs map to registered gallery users; unrecognized or unresolved failures remain `[unmapped Auth0 identity]`, never attributed from submitted usernames. Checkpoints are transactional and imports resume up to 400 records per click. Import again when backlog remains. Provider retention is plan-dependent: records can expire before a manual import, so this is not guaranteed complete archival coverage.
- **Snowflake:** a separate explicitly labeled button queries `SNOWFLAKE.ACCOUNT_USAGE.LOGIN_HISTORY` and can wake the warehouse. Each import overlaps the last seven days for current registered gallery users and deduplicates by provider event ID. Account Usage can lag two hours. These are account login events, including activity outside the gallery; they do not prove a gallery visit. Unknown users and deleted registry entries are excluded. A volume above 10,000 records rejects the import without saving a partial window.
- **Saved viewing:** status, timelines, daily totals and exports use Postgres. No scheduled imports, polling or idle warehouse queries were added. Auth0 and Snowflake records can represent the same sign-in and must not be summed as unique visits.
- **Retention:** raw events remain queryable for 90 days; aggregate UTC daily totals remain for 12 calendar months. PostgreSQL insert triggers maintain summaries atomically and deduplicated retries do not inflate them. Summaries omit search text and photo targets. Physical deletion is limited to once per day; the background coordinator may invoke the cleanup check while no user is active.
- **Exports:** detail CSV follows applied user/type/day filters; summary CSV follows user/type filters across 12 months. CSV cells neutralize spreadsheet formulas. Exports reject more than 50,000 rows and require narrower filters. No password, token, IP, user-agent or raw provider error payload is retained by the identity importer.

Add only `read:logs` to the existing management application's scopes; existing user-management scopes remain unchanged.
